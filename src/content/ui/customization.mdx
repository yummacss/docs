Every Yumma UI component gives you three levels of control, in the order you should reach for them: **props**, then `className`, then the file itself.

## Props first

Each component's API Reference table lists everything it accepts. Props are the reliable way to change a component, because the component applies them itself — there is no question of one class beating another.

```tsx
<Badge tone="subtle" color="green" size="lg" shape="pill">
  Shipped
</Badge>
```

Reach for the table before anything else. Most of what people try to do with `className` already exists as a prop.

## className, and what it cannot do

`className` is appended to the component's own classes. It is the right tool for anything the component leaves unset — a margin, `fs-0` in a flex row, positioning within your layout:

```tsx
<Badge className="ml-2">Shipped</Badge>
```

It is **not** a reliable way to override something the component already sets. Which of two utilities wins is decided by the generated stylesheet's rule order, not by the order you write them, and Yumma CSS has no `!important` escape hatch to force the issue:

```tsx
// Badge already sets a background. This may or may not win.
<Badge className="bg-blue-5">Shipped</Badge>

// Say it with the prop instead.
<Badge tone="solid" color="indigo">Shipped</Badge>
```

Where a component genuinely needs a per-instance override of something it already sets, it exposes a prop for exactly that rather than leaving you to fight the cascade. Skeleton's `size` replaces the shape's default dimensions instead of competing with them, and takes literal utilities so the class scanner can still see them in your source:

```tsx
<Skeleton shape="circle" size="w-9 h-9" />
```

Toggle's `swatchClassName` works the same way, replacing `tone` for a color-picker swatch.

## The file is yours

`yummaui add` copies a real file into your project — it is not a dependency, and nothing overwrites it later. When props and `className` are not enough, edit it.

This is the level to use for anything structural: changing the markup, swapping an icon set, dropping an animation, or wiring in behaviour the component does not have. Each component is a single self-contained file, so there is no shared abstraction to work around.

Components are built on [Base UI](https://base-ui.com), so the primitive underneath is documented there — useful the moment you start editing. Pages built on a primitive link to it directly.

## Colors and theme

Component colors come from Yumma CSS, so they are configured in `yumma.config.mjs` rather than anywhere in Yumma UI. Adding a brand color or changing how shades are generated is covered in [Colors](/docs/colors) and [Configuration](/docs/configuration).
