### Resolved

- **#7 deferred.** `@` means "compiles to an `@media` wrapper" (`@sm`, `@pc`).
  That is only honest if the variant compiles to
  `@media (prefers-color-scheme: dark)` - but the useful behaviour is
  following a manual toggle, which is a selector, not an at-rule. Since the
  token layer already handles both OS preference & manual toggle via
  `color-scheme`, the escape hatch is not needed yet. Design it when a real
  case appears; that case will also settle the notation.
- **#11 dropped.** `gtc-1` … `gtc-16` already generate
  `repeat(N, minmax(0, 1fr))`, and `gtc-s` / `gtr-s` already generate
  `subgrid`. A `fr` variant would differ from `gtc-1` only in `1fr` vs
  `minmax(0, 1fr)` - a real difference in shrink behaviour, but two
  near-identical classes is a footgun & `minmax(0, 1fr)` is usually wanted.
- **#15 rejected.** Clean break, no dual-syntax parser. The user base is one
  person who will be migrated by hand. The codemod (#12) is still required.
- **`subtle` token contrast.** Measured against the real gray scale, no single
  value passes AA in both schemes: `gray-6` is 3.66 on white, `gray` is 3.88
  on `gray-12`. Resolved by making it a pair like every other token -
  `light-dark(gray, gray-6)` gives 4.83 light / 5.13 dark, both passing, & it
  still sits below `muted` (6.13 / 6.56) in the hierarchy.

- **#6b rejected.** No built-in `page` / `surface` / `fg` vocabulary. Dark mode
  is opt-in per color: every utility color applies in both schemes as it always
  has, & a user who wants a specific color to differ in dark mode defines it as
  a pair. Shipping 11 opinionated names would claim namespace & impose a design
  system on people who only wanted one color to change. The token table from
  the earlier draft is still a sound recipe - it belongs in the docs as an
  example, not in core.
- **#13 needs no work.** Verified against a running `next dev`: editing
  `yumma.config.mjs` propagates to the served CSS in roughly ten seconds with
  no source file touched & no restart. `loadConfig` busts the ESM import cache
  with the file's mtime, & the PostCSS plugin registers the config path as a
  `dependency` message, so Turbopack watches it. Both landed in 3.26.

  Debugging note: dev CSS is minified, so `#ff00ff` is served as `#f0f`. Use a
  color that cannot be shortened to three digits when grepping generated
  output, or the change looks like it never happened.
- **#16 OKLCH, deferred to 4.0.** Shades are mixed toward white & black in
  sRGB. Hue holds up well - under 10 degrees of drift across every default hue
  - but lightness spacing collapses on light-native hues. Measured spread
  between the largest & smallest step: blue 23%, red 103%, magenta 160%,
  cyan 226%, lime 261%, **yellow 460%**. So `yellow-1` through `yellow-6` are
  nearly indistinguishable while the dark end plummets. OKLCH fixes this, but
  it changes every generated color value, which is major-only. `tinycolor2`
  cannot parse `oklch()` or `lch()` at all, so it also needs a new colour
  library or hand-rolled matrices. Shade generation is now isolated inside
  `generateShades` so the swap stays contained.
- **#17 rejected.** Renaming shades to 50/100/200 imports the identity 4.0
  exists to move away from, breaks every class name, grows the codemod, and
  renders nothing differently. The current 1-12 scale with an unnumbered base
  at the midpoint is monotonic & works.

**~~`node:fs` leaks into the browser bundle~~ FIXED 2026-07-28 - unpublished**

The playground had been failing to deploy since v3.26.0 & is serving a stale
v3.26.0 build, which is why `cs-ld` & other 3.29 utilities have no completions
or hover there.

```text
the chunking context does not support external modules (request: node:fs)
Import traces: Client Component Browser: ./src/app/page.tsx
```

The culprit was one line. `intellisense/src/validate.ts` imported
`suggestClasses` / `validateClasses` from `@yummacss/nitro` - the **root**
entry, which re-exports `loadConfig` & `scan` & therefore reaches `node:fs`,
`node:crypto` & `tinyglobby`. The Monaco adapter imports `findUnknownClasses`
from that same module, so the Node-only surface rode into the browser bundle.
A `./browser` entry already existed on `nitro`; nothing was pointing at it.

The fix (in the monorepo, on `main`, uncommitted):

- `nitro/src/browser.ts` also exports `suggestClasses`, `validateClasses` &
  the `Config` / `ValidationResult` types. All live in `generator.ts`, which
  only ever depended on `@yummacss/core` - already browser-safe.
- `intellisense/src/validate.ts` imports from `@yummacss/nitro/browser`.
- `adapters/monaco.ts` takes its `Config` type from `/browser` too. Type-only,
  so it changes no output - it keeps the browser-facing file honest.

Verified by building `play` against the local packages: the committed state
reproduces the exact reported error (Turbopack, **9 errors**, trace running
`monaco.mjs` -> `validate-*.mjs` -> `nitro/dist/index.mjs` -> `tinyglobby` ->
`fdir`); with the fix linked in, **4 errors**, zero mentioning `node:fs`.
`play` was restored to its committed state afterwards.

**Still not deployable - a second, unrelated blocker.** Those remaining 4
errors are `react-resizable-panels`. `play` is on 4.12.1 but `page.tsx` still
imports the v3 API: v4 renamed `PanelGroup` -> `Group` and
`PanelResizeHandle` -> `Separator`. This is pre-existing & independent of the
`node:fs` work - it must be migrated before play can deploy, and it is UI
work, not a package-boundary fix.

Two things remain before the playground recovers:

1. Publish the monorepo fix, then bump `play`'s `@yummacss/intellisense`.
2. Migrate `page.tsx` to the `react-resizable-panels` v4 API.

Related: exposing `yumma.config.mjs` in the playground needs config loading to
work browser-side. That is still open - `loadConfig` is genuinely Node-only,
so it needs a browser config path, not just a re-export.

Note `play`'s production branch is `release`, not `main`.

**Docs build OOM on Vercel - measured 2026-07-27**

Vercel's builder is 2 cores / 8 GB. The build dies during "Creating an
optimized production build" - the Turbopack compile, before page generation -
so `experimental.cpus` cannot help; it only caps the later worker pools.

Peak node RSS for a full local build, sampled from the process tree. **Treat
these as unreliable** - see the warning below.

| Configuration | Peak RSS |
| --- | --- |
| Baseline (450 registry entries, Shiki, 11 grammars) | 10,086 MB |
| Registry stubbed 450 -> 20 (606 chunks -> 44) | 8,822 MB |
| Shiki disabled entirely | 3,561 MB |
| Shiki with 1 grammar | 4,354 MB |
| Shiki, JS RegExp engine, 11 grammars | 9,698 MB |
| Pinned to 2 cores via processor affinity | 9,023 MB |
| Shiki reduced to 6 distinct grammars | **11,904 MB** |

**These were single runs, and the last row proves they are noisy.** Cutting
grammars from 11 to 6 measured *higher* than the baseline, which is impossible
as a real effect. Run-to-run variance is therefore at least ~18%, so every
difference smaller than that - the registry, the JS engine, the grammar count -
is inside the noise floor & means nothing. Only the Shiki-disabled result
(-65%) is large enough to survive.

Anyone repeating this: run each configuration several times & compare medians,
on a machine that resembles the 2-core builder. Peak RSS on a workstation with
spare RAM is inflated anyway, because allocators & V8 grow lazily when memory
is cheap.

What can still be said:

- **Shiki is a major cost** - disabling it drops peak by roughly two thirds.
  Nothing finer-grained than that is established.
- **The registry is not the cause**, or at least not measurably so. Moving it
  into a separate package would not help regardless: the docs still bundle
  whatever they render, so packaging relocates the cost rather than removing
  it.
- **Trimming grammars is unproven.** `js`/`mjs`/`cjs` share one grammar, as do
  `bash`/`sh`/`shell`/`zsh`, so 11 ids are 10 distinct grammars; `jsx`, `json`,
  `diff` & `ts` are 1-5 uses each & could go, but the measured effect was
  noise.
- ~~**CAUSE CONFIRMED: the build cache.**~~ **WRONG - FALSIFIED 2026-07-28.**
  A deploy of commit `31c5c20` logged `Skipping build cache, deployment was
  triggered without cache` at 10:21:26 & still died with SIGKILL at 10:22:32
  during "Creating an optimized production build". The cache correlation was
  real but not causal; it was noise of the same kind that produced the
  incoherent table above. `VERCEL_FORCE_NO_BUILD_CACHE=1` does not fix this &
  is not worth setting.
- **Current hypothesis: nested async chunking over 450 dynamic imports.**
  `experimental.turbopackClientSideNestedAsyncChunking` defaults to **true** in
  build mode. Next's own description: "computes all possible paths through
  dynamic imports in the applications to figure out the modules needed at
  dynamic imports for every path." `src/registry/index.ts` holds 450 dynamic
  imports in a single object, reached from `component-preview.tsx` &
  `preview.tsx`. Set to `false` in `next.config.ts` on 2026-07-28, together
  with `turbopackSourceMaps: false`. **Unverified** - a local build only proves
  the config is accepted & the site still compiles; the 2-core builder is the
  only real test.
- **Not measured locally, deliberately.** Peak-RSS runs on a Windows
  workstation carry the ~18% variance documented above & are inflated by spare
  RAM, so they cannot separate these flags. One Vercel deploy settles it.
- **Paid escape hatch, if it comes to that.** Vercel's larger build machines
  are billed per CPU-minute ($0.0035/CPU-min; the 8-CPU Enhanced tier is
  $0.028/min) on paid plans. Not free, so not the default answer.
- **This buys headroom, it does not create it.** The build still sits near the
  memory ceiling; the cache was what pushed it over. As the docs grow the limit
  returns, so **splitting into two Vercel projects** (utility docs & UI docs)
  is still the durable fix - & it does not depend on any measurement above
  being right.

Reducing chunk count is still worth doing on its own merits - 606 chunks for 38
component pages - but as cleanup, not as an OOM fix. The playground idea (one
live preview with a settings panel, replacing hundreds of prebuilt demos) is
the version that would genuinely shrink the build.

## Post draft

Everything below is prose for the published post. Sections stay commented out
until the feature actually ships.

Yumma CSS 4.0 changes how every utility is written. `-` becomes `:` between a
property & its value, which makes the class a compressed form of the
declaration it generates.

```html del={1} ins={2}
<div class="d-f jc-c ai-c"></div>
<div class="d:f jc:c ai:c"></div>
```

The rule is one line: `:` separates property from value, `-` subdivides a value.

```html
<div class="bg:gray-1 c:blue-4"></div>
```

Negative values stop being a special case. `m--4` was a parser artifact leaking
into the API - `m:-4` is the declaration with the whitespace removed.

```html del={1} ins={2}
<div class="m--4"></div>
<div class="m:-4"></div>
```

Variants keep their prefix position. `h:bg:gray-1` groups & sorts predictably,
& `h:` stays greppable.
